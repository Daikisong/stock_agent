## 1. 지금 어떤 방식으로 진행 중인가

현재 작업은 점수가 낮다는 이유로 문서나 fact를 계속 추가하는 방식이 아니다. 각 종목의 target leaf에서 `RESEARCH_CHECKPOINT_PENDING`을 만든 정확한 completion gate를 찾고, 그 gate를 만든 실제 데이터 계보만 수리한 뒤 같은 checkpoint를 clean resume하고 있다.

쉬운 예:

- 저장된 값이 문자열 `"104.1"`이면 exact grounding은 따옴표까지 포함한 JSON 문자열을 요구한다.
- 하지만 분석 모델은 이를 자연스럽게 숫자 `104.1`로 반환했다.
- 둘의 경제적 의미는 같아 보여도 재현 가능한 exact grounding에서는 타입이 다르므로 component가 pending이 됐다.
- 해결은 비교를 느슨하게 만드는 것이 아니라, 원래 숫자인 값을 EvidenceFact에 숫자로 저장하도록 원천 타입을 복원하는 것이다.

현재 production 흐름은 아래 순서로 진행된다.

1. 기존 문서·claim·fact를 `as_of_date` 기준으로 재개한다.
2. fact 값의 손상된 표현과 원래 JSON 타입만 복원한다.
3. business-model memo를 다시 만든다.
4. 7개 component를 각각 여러 loss-accounted 청크로 검토한다.
5. 각 청크는 source value, period, predicate, economic mechanism을 exact 대조한다.
6. 최초 응답이 원문 필드를 요약하면 격리하고 1회 교정한다.
7. 모든 청크와 synthesis가 `research_complete=true`여야 해당 component가 닫힌다.
8. 이후 Judge, Red Team, Supervisor, deterministic score, `score_valid=true`, FINAL StageCourt로 진행한다.
9. production complete 뒤에만 격리된 Gold post-run comparison을 수행한다.

### 2.3 JSON 객체가 문자열로 저장된 타입 오염

- 영향: `valuation_rerating` 마지막 청크의 `68.1`, `755` 행에서 exact JSON 타입 불일치.
- 수리: 완전한 JSON object/array 문자열만 native object/list로 복원했다.
- 실제 삼성 결과:
  - structured JSON 문자열 `370 → 0`
  - native object/list 복원 `370`
  - claims `8118 → 8118`

- 커밋: `3a072c0c JSON 문자열로 오염된 사실 값 타입 복원`

### 2.4 명백한 정량값이 문자열로 저장된 타입 오염

  - 단일 finite quantitative point는 JSON number로 보존한다.

- 보존 예:

### 2.6 production이 backfill 방식으로 실행되던 모드 오염

- 정확한 증상:
  - Phase94는 production runner인데 source acquisition mode가
    `RESEARCH_BACKFILL`로 하드코딩돼 있었다.
  - fact extractor도 현재 Supervisor 공백이 아니라 긴 문서 전체의 모든
    경제 문장을 소진하도록 동작했다.
  - `CUSTOMER_OFFICIAL`을 요청한 검색에서 일반 Tistory 해설이 material로
    fetch됐다.
- 실제 영향:
  - 18,352자 일반 HBM 해설 하나에서 9페이지 × 12개 = 108개 fact 제안이
    나왔다.
  - 대부분 HBM/GDDR 구조·역사·일반 경쟁 설명으로, 아래 7개 Supervisor
    공백을 직접 닫지 못했다.
  - canonical ledger에는 materialization 전 중지해 추가되지 않았다.
- 수리:
  - Phase94 기본 source mode를 `PRODUCTION_DAILY`로 고정했다.
  - 기존 backfill checkpoint는 production으로만 한 방향 승격하고,
    과거 transport 수로 completion을 인증하지 못하게 했다.
  - production fact마다 document-linked current `objective_ids`와
    `ADVANCE/COUNTER/SUPERSEDE` 관계를 LLM이 명시하게 했다.
  - deterministic 코드는 목적 roster·문서 계보·원문 인용만 검증하고
    경제적 관련성 판단은 LLM에 남겼다.
  - `CUSTOMER_OFFICIAL` 같은 source 요청은 실제 요청 family와 일치한다고
    LLM이 판정한 후보만 material fetch할 수 있게 했다. 블로그·재전재는
    공식 source를 언급해도 `NONE`이다.
- 손실 방지:
  - 12개는 계속 한 페이지의 전송 한도일 뿐 전체 fact 상한이 아니다.
  - 현재 목적에 실제 관련된 사실이 13개면 12+1 두 페이지로 모두 보존한다.

### 2.8 동일 URL의 구형 material 판정 재사용 우회

- 첫 production resume에서 새 후보 24개는 새 source-family 계약으로 모두
  정상 탈락했다.
- 그러나 동일 URL을 과거 checkpoint에서 이미 본 적이 있으면 candidate id가
  재사용됐고, 새 query/objective/source family만 합쳐진 채 과거
  `MATERIAL_PENDING_FETCH` 판정이 유지됐다.
- 그 결과 `CUSTOMER_OFFICIAL` query가 Brunch/Tistory/Newneek 같은 구형
  후보를 다시 LLM 심사하지 않고 fetch하는 우회가 확인됐다.
- canonical fact 반영 전 실행을 중단했다.
- 수리:
  - 동일 URL에 새 objective/source scope가 붙으면 이전 material 판정을
    무효화하고 새 LLM source-family 심사를 받는다.
  - production fetch 직전 현재 scope hash와 실제 matched source family를
    다시 확인한다.
  - 이미 canonical fact의 exact quote source인 backfill 문서는 역사 증거로
    보존한다.
  - 아직 canonical fact로 검증되지 않은 구형 fetched backlog는 새 source
    판정 통과 전까지 production fact/Supervisor 입력에서 제외한다.
- 검증:
  - 정확한 우회 재현 테스트 4개 추가
  - source/Phase94/Researcher/Supervisor 관련 165개 테스트 통과
