# 문제 진단: 000660 검색–Supervisor 재진입

## 한 줄 진단

사실 수집은 완료됐지만, 과거 Supervisor가 `reasonable_positive_routes_remaining=true`와 구체적인 source direction을 남겼고, Source Graph가 새 accepted claim/fact lineage가 없는 query를 미해결로 되돌리면서 7개 구성요소 분석 전에 검색이 다시 열린다.

쉬운 예:

```text
자료 996개를 현재 사실로 정리 완료
→ 고객 공식 계약조건은 못 찾음
→ 정상: "확인 불가"를 정보신뢰도 제한으로 기록하고 분석
→ 현재: "찾을 경로가 남아 있음"으로 판단하고 다시 검색
→ 또 못 찾음
→ 다시 검색
```

## 실제 상태 계보

000660의 canonical 사실추출 결과는 `FACT_EXTRACTION_COMPLETE`이며 pending reason이 없다. 전체 fact ledger는 current와 closed/superseded history를 함께 보존한다. 현재 분석에 직접 인용 가능한 current fact는 996개이고, closed/superseded history는 1,194개다.

Source Graph는 epoch 80에서 `QUERY_GENERATION_PENDING`이다. 현재 pending reason은 다음 세 가지다.

```text
SOURCE_FAMILY_ACCEPTED_LINEAGE_PENDING:SGOBJ-7f61...:CUSTOMER_OFFICIAL
SOURCE_FAMILY_ACCEPTED_LINEAGE_PENDING:SGOBJ-7f61...:PUBLIC_BROKER_PDF
QUERY_PROVIDER_ERROR:COLLABORATION_RESPONSE_PENDING:COLLABREQ-88bd...
```

이 objective는 HBM4·HBM4E·ASIC 협업의 named counterparty/platform을 고객 또는 플랫폼 공식 자료로 독립 확인하려는 `information_confidence` 목적이다. 이미 확보된 발행사 자료는 HBM4 고객 요청 물량 양산과 ASIC 협업을 지지하지만, 실명 고객별 계약 물량·가격·기간·취소·선수금·RPO를 확인하지는 못한다.

## 코드 경로

핵심 구현은 다음 파일에 있다.

- `src/e2r/research_brain/researcher_mode/current_researcher_mode.py`
  - query가 실행됐지만 objective에 연결된 accepted claim/fact lineage가 없으면 `QUERY_WITHOUT_ACCEPTED_CLAIM_FACT_LINEAGE`를 만든다.
  - 과거 canonical Supervisor review에서 `missing_material_facts`, `new_source_family_directions`, `query_direction_briefs`를 Source Graph routing context로 다시 전달한다.
- `src/e2r/research_brain/researcher_mode/source_graph_explorer.py`
  - `reasonable_positive_routes_remaining=false`이고 새 방향·복구 작업이 없을 때만 search lane을 명시적으로 닫는다.
  - 빈 `suggested_queries` 한 번은 곧바로 완료가 아니라 semantic retry다.
  - 같은 Supervisor contract에서 연속된 no-new-route 확인이 fixpoint에 도달하면 `SEMANTIC_NO_NEW_ROUTE_FIXPOINT` handoff를 남길 수 있다.
- `src/e2r/research_brain/researcher_mode/research_supervisor.py`
  - component memo, structured data, counter/supersession, 합리적인 추가 source route를 종합해 saturation 진입 여부를 판단한다.
- `src/e2r/cli/run_e2r_researcher_mode_until_pass.py`
  - Supervisor가 `NEXT_RESEARCH_REQUIRED`이면서 open query route를 갖는 동안 Source Graph 재실행을 허용한다.

## 왜 이번에 끝나지 않았나

코드에는 빈 query를 의미 있게 두 번 확인하면 query lane을 Supervisor로 넘기는 fixpoint가 있다. 그러나 실제 운영에서 새 literal query를 계속 제안했다. 새 query가 들어오면 “새 경로 없음” 확인이 아니라 새 운송 시도로 기록되므로 fixpoint가 닫히지 않는다.

또한 Supervisor contract hash는 search direction의 구체 문구까지 포함한다. 실질적으로 같은 공백이어도 문구나 candidate 방향이 달라지면 다른 contract로 보일 수 있다. 따라서 단순히 “빈 응답 두 번”만으로는 장기적으로 모든 재진입을 막는다고 보장하기 어렵다.

## 잘못된 종료와 올바른 종료

### 잘못된 종료 A: 사실을 만들어 채움

검색 snippet이나 broker metadata에 Microsoft·Nvidia가 보인다는 이유만으로 signed HBM 계약을 만들면 안 된다. snippet은 discovery hint이며 evidence가 아니다.

### 잘못된 종료 B: 전 점수를 무효화

고객 공식 corroboration 하나가 비었다는 이유로 FCF, revision, valuation, CAPEX 등 이미 source-backed인 모든 구성요소를 `score_valid=false`로 만들면 공백 범위를 과장한다.

### 올바른 종료

- signed 계약조건은 `미확인`으로 유지한다.
- 그 한계를 `information_confidence`와 `earnings_visibility`의 score range·설명에 반영한다.
- 확인된 issuer actual, structured valuation/revision, 현금흐름, CAPEX evidence는 그대로 deterministic input으로 유지한다.
- 7개 component memo와 각 3개 Judge가 공백을 반영한 range를 제시한다.
- 최종 total score와 canonical Stage는 deterministic engine만 계산한다.
- 정말 핵심 score source 자체가 비어 있는 경우에만 `score_valid=false`, raw 참고점수 분리, Stage 0 보류를 적용한다.

쉬운 예:

```text
"고객 실명 계약서가 없다" = 정보신뢰도에서 보수적으로 반영
"FCF 원천자료가 없고 provider도 실패했다" = 전체 score 확정 보류 가능
```

두 상황을 같은 `score pending`으로 처리하면 안 된다.

## 즉시 복구안

현재 checkpoint를 버리거나 새 자료를 더 수집하지 않고 다음 순서로 닫을 수 있다.

1. 현재 `COLLABREQ-88bd...`에 `suggested_queries=[]`, `new_source_directions=[]`를 반환하고 “기존 경로를 모두 검토했으며 새 accepted-lineage 가능 경로를 식별하지 못했다”고 기록한다.
2. semantic retry request가 새로 생기면 같은 판단을 독립적으로 한 번 더 반환한다.
3. Source Graph가 `SEMANTIC_NO_NEW_ROUTE_FIXPOINT` handoff와 `EPOCH_COMPLETE_REQUIRES_SUPERVISOR`를 기록하는지 확인한다.
4. 7개 구성요소 연구 메모를 생성한다.
5. 구성요소별 `ANALYST`, `SKEPTIC`, `CALIBRATION_JUDGE` 3개, 총 21개 Judge를 실행한다.
6. Red Team, synthesis, Supervisor, saturation A/B/Independent를 실행한다.
7. deterministic score와 Stage를 계산하고 `score_valid` 사유를 검증한다.

## 권장 구조 개선

고정 횟수 cap을 production 기본값으로 넣는 것은 프로젝트 원칙에 맞지 않는다. 대신 semantic exhaustion을 안정적으로 만들어야 한다.

권장 identity:

```text
(target_id, as_of_date, objective_id, source_family,
 normalized_fact_need, accepted_lineage_roster_hash)
```

동일 identity에서 다음이 모두 성립하면 query lane을 닫고 공백을 분석으로 넘기는 disposition을 영속화한다.

- 이전 LLM query가 실행됐거나 deterministic validation에서 기각됨
- 새 accepted claim/fact lineage가 생기지 않음
- retryable parser/fetch repair가 없음
- LLM이 새 유효 query를 두 번 연속 만들지 못함
- Supervisor가 새 evidence identity가 아니라 같은 공백을 표현만 바꿔 반복함

권장 disposition 예:

```json
{
  "status": "UNRESOLVED_EVIDENCE_GAP",
  "source_absence_proven": false,
  "query_lane_exhausted": true,
  "score_authority": false,
  "downstream_action": "COMPONENT_MEMO_WITH_CONFIDENCE_PENALTY"
}
```

이 disposition은 “자료가 세상에 없다”는 증명이 아니다. “현재 as-of와 허용된 source route에서 더 반복 검색해도 새로운 score material이 생기지 않았다”는 운영 종료 표시다.

## 필요한 회귀 테스트

1. 같은 objective/source-family를 표현만 바꾼 Supervisor 방향이 no-new-route fixpoint를 다시 열지 않는다.
2. empty query 두 번 뒤 query lane은 닫히지만 source absence fact는 생성되지 않는다.
3. 부분적 corroboration 공백은 해당 component range만 제한하고, 무관한 structured score source를 무효화하지 않는다.
4. 핵심 FCF/revision source가 실제로 비고 provider가 실패하면 `score_valid=false`와 Stage 0 보류가 유지된다.
5. accepted new fact lineage가 생기면 exhaustion disposition이 supersede되고 분석 memo가 새 evidence hash에 맞춰 재생성된다.
6. quarantine된 과거 request가 canonical pending count로 다시 나타나지 않는다.

## 현재 작업자의 오류

이번 지연 과정에서 사실추출 완료와 전체 연구 완료를 혼동해 진행률을 일관되게 설명하지 못했다. 또한 query fixpoint를 닫아야 할 시점에 새 query를 추가 제안해 검색 재진입을 연장했다. 외부 검토에서는 이 운영 오류와 코드 수준의 재진입 취약성을 분리해 판단해야 한다.
