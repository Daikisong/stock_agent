# 000660 Gate 1 문제점과 수정 결과

## 결론

000660 C06 연구는 새 자료를 더 찾지 않고 기존 fact 장부로 끝까지 계산됐다.

```text
7개 component memo: 7 / 7
Judge: 21 / 21
Red Team: COMPLETE
synthesis: COMPLETE
Supervisor: READY_FOR_INDEPENDENT_SATURATION_REVIEW
saturation: CERTIFIED (A / B / Independent)
deterministic score: 70.2
score interval: 68.153813 ~ 72.246187
score_valid: true
canonical Stage: 2
StageCourt: FINAL
동일 입력 재실행 신규 query/fetch: 0 / 0
```

이 문서의 Stage는 투자 지시가 아니라 E2R 상태기계의 재현 결과다.

## 왜 무한 반복됐나

문제는 자료의 양이 아니라 종료 조건이었다.

1. Supervisor 문구가 조금 바뀔 때 같은 공백이 새 공백처럼 보일 수 있었다.
2. 고객 공식 확인 같은 보조 corroboration 공백이 FCF·revision·valuation까지 전부 막을 수 있었다.
3. 검색해도 새 근거가 나오지 않았다는 상태를 source absence와 구별해 영속적으로 저장하지 못했다.
4. 같은 route를 다시 열지 말아야 한다는 semantic fixpoint가 약했다.
5. downstream이 모두 끝난 뒤에도 과거의 `zero_result_only` 기록 하나가 Supervisor를 영구 차단했다.

쉬운 예를 들면, 계약서의 가격 조항을 못 찾았다고 이미 공시된 영업현금흐름까지 없는 것으로 취급한 셈이다. 이번 수정은 계약조건 공백은 `earnings_visibility`와 `information_confidence` 상단만 제한하고, 현금흐름·실적·valuation 근거는 그대로 계산하게 한다.

## 무엇을 고쳤나

### 1. 같은 공백의 안정적인 신분증

`EvidenceGapKey`는 Supervisor 문장이나 query 문구가 아니라 다음 구조로 같은 공백을 식별한다.

- target / cutoff / archetype
- stable objective
- 영향을 받는 component
- 필요한 source family
- economic mechanism / fact need
- 현재 fact snapshot hash
- accepted lineage roster hash

따라서 “고객 공식 계약 확인 부족”과 “고객사 직접 물량·가격 근거 미확인”은 같은 구조적 공백으로 닫힌다.

### 2. 공백의 영향 범위 분리

현재 공백은 `CORE_SCORE_BLOCKER`가 아니라 `CORROBORATION_CAP`으로 판정됐다.

```text
영향받음: earnings_visibility, information_confidence
그대로 계산: eps_fcf_explosion, bottleneck_pricing,
             market_mispricing, valuation_rerating, capital_allocation
```

### 3. 검색 종료 상태를 append-only로 보존

`EGAPDISP-5f2f9b9418ecc7f2b9eed09e`는 source absence를 주장하지 않는다. 현재 snapshot과 이미 시도한 route에서는 새 점수 재료가 나오지 않았으므로 분석으로 넘긴다는 뜻이다.

재개방은 새 fact, 새 accepted lineage, 실제 새 source route, provider/parser 복구, 새 current event가 생긴 경우에만 허용된다.

### 4. 두 번의 독립 no-new-route 확인과 세 번째 차단

서로 다른 prompt hash를 가진 두 응답이 모두 새 query와 새 source direction을 0개로 반환했다. 그 결과 `SEMANTIC_NO_NEW_ROUTE_FIXPOINT`가 만들어졌다. 같은 snapshot에서 세 번째 동일 query를 열면 `REPEATED_EXHAUSTED_GAP_REOPENED` hard failure가 난다.

### 5. 과거 빈 검색의 영구 차단 버그 수정

`research_supervisor._failure_blocks_readiness`는 이전에 historical `zero_result_only`면 무조건 현재 blocker로 취급했다.

이제는 다음처럼 구분한다.

- retryable 또는 `INSUFFICIENT_SEARCH`: 현재 blocker
- 유효한 source-absence proof: 규칙에 따라 처리
- non-retryable `DUPLICATE_QUERY`: 완료된 memo를 다시 열지 않음

빈 검색 자체는 여전히 saturation이나 source absence 증명이 아니다.

## 숫자가 왜 2,190 / 996 / 831로 다르나

- 2,190: historical lineage까지 포함한 전체 EvidenceFact 수
- 996: `CURRENT` 또는 `OPEN`인 동결 fact 수
- 831: StageCourt에 직접 인용 가능한 current/open fact를 eligibility와 citable lineage 규칙으로 투영한 수

예를 들어 superseded historical broker forecast는 전체 장부 2,190에는 남지만 현재 Stage를 정하는 831개에는 들어가지 않는다. 삭제한 것이 아니라 역할을 분리한 것이다.

## Stage 2가 된 이유

총점은 70.2이고 deterministic StageCourt는 Stage 2를 냈다. Green gate 네 primitive 중 두 개가 최종 present-positive 조건을 충족하지 못했다.

- `customer_preorder_or_allocation`: 고객 요청 물량 양산 mapping은 있으나 독립 source quorum 미충족
- `hbm_capacity_pre_sold`: CAPA 선판매·예약·완판 근거 없음

쉬운 예로 “고객이 요청한 HBM4 물량을 지금 양산한다”는 문장을 “향후 생산능력이 전량 장기 예약됐다”로 바꾸지 않았다.

## 남아 있는 한계

다음은 점수 상단과 confidence를 제한하지만 현재 score blocker는 아니다.

- HBM-only 매출·마진·FCF가 전사 actual과 완전히 분리되지 않음
- 고객별 signed 물량·가격·기간·취소·선수금·backlog/RPO 미확인
- HBM 전용 locked CAPA, sold-out 기간, realized ASP의 정량 근거 미확인

새 자료를 못 찾았다는 사실을 계약 부재로 바꾸지 않았고, 낮은 점수나 Stage 0으로 강제 종료하지도 않았다.

## 원본과 재현성

원본 `output/researcher_mode/c06/2026-07-12-clean-v8/`의 source corpus, 2,190 facts, 36 documents는 수정되지 않았다. copy-on-write root에서 계산했으며 source와 fact 파일 hash는 원본과 같다.

동일 입력 재실행에서는 request, response, query, fetch, document, fact, score, Stage 파일이 하나도 변하지 않았다. 세부 수치는 `identical_rerun_audit.json`에 있다.
