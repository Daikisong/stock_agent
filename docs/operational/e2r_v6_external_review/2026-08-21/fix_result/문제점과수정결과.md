# 000660 Gate 1 문제점과 수정 결과

## 결론

000660 C06 연구는 새 자료를 더 찾지 않고 기존 fact 장부로 끝까지 계산됐다.

```text
7개 component memo: 7 / 7
Judge: 21 / 21
Red Team: COMPLETE
synthesis: COMPLETE
Supervisor: READY_FOR_INDEPENDENT_SATURATION_REVIEW
saturation: CERTIFIED (A / B / Independent)
deterministic score: 70.2
score interval: 68.153813 ~ 72.246187
score_valid: true
canonical Stage: 2
StageCourt: FINAL
동일 입력 재실행 신규 query/fetch: 0 / 0
```

이 문서의 Stage는 투자 지시가 아니라 E2R 상태기계의 재현 결과다.

## 왜 무한 반복됐나

문제는 자료의 양이 아니라 종료 조건이었다.

1. Supervisor 문구가 조금 바뀔 때 같은 공백이 새 공백처럼 보일 수 있었다.
2. 고객 공식 확인 같은 보조 corroboration 공백이 FCF·revision·valuation까지 전부 막을 수 있었다.
3. 검색해도 새 근거가 나오지 않았다는 상태를 source absence와 구별해 영속적으로 저장하지 못했다.
4. 같은 route를 다시 열지 말아야 한다는 semantic fixpoint가 약했다.
5. downstream이 모두 끝난 뒤에도 과거의 `zero_result_only` 기록 하나가 Supervisor를 영구 차단했다.

쉬운 예를 들면, 계약서의 가격 조항을 못 찾았다고 이미 공시된 영업현금흐름까지 없는 것으로 취급한 셈이다. 이번 수정은 계약조건 공백은 `earnings_visibility`와 `information_confidence` 상단만 제한하고, 현금흐름·실적·valuation 근거는 그대로 계산하게 한다.

## 무엇을 고쳤나

### 1. 같은 공백의 안정적인 신분증

`EvidenceGapKey`는 Supervisor 문장이나 query 문구가 아니라 다음 구조로 같은 공백을 식별한다.

- target / cutoff / archetype
- stable objective
- 영향을 받는 component
- 필요한 source family
- economic mechanism / fact need
- 현재 fact snapshot hash
- accepted lineage roster hash

따라서 “고객 공식 계약 확인 부족”과 “고객사 직접 물량·가격 근거 미확인”은 같은 구조적 공백으로 닫힌다.

### 2. 공백의 영향 범위 분리

현재 공백은 `CORE_SCORE_BLOCKER`가 아니라 `CORROBORATION_CAP`으로 판정됐다.

```text
영향받음: earnings_visibility, information_confidence
그대로 계산: eps_fcf_explosion, bottleneck_pricing,
             market_mispricing, valuation_rerating, capital_allocation
```

### 3. 검색 종료 상태를 append-only로 보존

`EGAPDISP-5f2f9b9418ecc7f2b9eed09e`는 source absence를 주장하지 않는다. 현재 snapshot과 이미 시도한 route에서는 새 점수 재료가 나오지 않았으므로 분석으로 넘긴다는 뜻이다.

재개방은 새 fact, 새 accepted lineage, 실제 새 source route, provider/parser 복구, 새 current event가 생긴 경우에만 허용된다.

### 4. 두 번의 독립 no-new-route 확인과 세 번째 차단

서로 다른 prompt hash를 가진 두 응답이 모두 새 query와 새 source direction을 0개로 반환했다. 그 결과 `SEMANTIC_NO_NEW_ROUTE_FIXPOINT`가 만들어졌다. 같은 snapshot에서 세 번째 동일 query를 열면 `REPEATED_EXHAUSTED_GAP_REOPENED` hard failure가 난다.

### 5. 과거 빈 검색의 영구 차단 버그 수정

`research_supervisor._failure_blocks_readiness`는 이전에 historical `zero_result_only`면 무조건 현재 blocker로 취급했다.

이제는 다음처럼 구분한다.

- retryable 또는 `INSUFFICIENT_SEARCH`: 현재 blocker
- 유효한 source-absence proof: 규칙에 따라 처리
- non-retryable `DUPLICATE_QUERY`: 완료된 memo를 다시 열지 않음

빈 검색 자체는 여전히 saturation이나 source absence 증명이 아니다.

## 독립 검수에서 추가로 발견한 generic 결함과 수정

초기 000660 영수증은 내부적으로 일관됐지만, 다른 종목·다른 공백에도 안전한지는 별개였다. 독립 검수에서 다음 네 문제를 확인했다.

### 1. 다른 공백의 빈 응답 재사용 차단

이전에는 누적 `query_generation_history`의 빈 응답을 현재 gap의 응답처럼 다시 라벨링할 수 있었다. 이제 각 history row에 다음 exact binding을 저장하고 모두 일치할 때만 confirmation으로 인정한다.

- `evidence_gap_key`
- `semantic_gap_id`
- `objective_identity`
- `fact_snapshot_hash`
- `accepted_lineage_roster_hash`
- `required_source_family`

쉬운 예: FCF 공백 A에서 받은 “새 query 없음” 답을 고객 계약 공백 B의 답으로 재사용할 수 없다.

### 2. acquisition 종료를 gap별 coverage로 변경

이전에는 nonblocking disposition 하나가 있으면 전체 source acquisition을 끌 수 있었다. 이제 pending failure를 stable objective별 gap으로 재구성하고, 모든 gap이 각자의 exact nonblocking disposition으로 덮였을 때만 종료한다. 하나라도 `CORE_SCORE_BLOCKER`이면 pending을 유지한다. source transport pending도 corroboration disposition과 무관하게 계속 처리한다.

쉬운 예: 고객 corroboration A가 cap으로 닫혔어도 FCF 원문 parser 실패 B는 계속 blocker다.

### 3. raw fact count 대신 source family × economic role 정책

component에 fact가 1개 있다는 이유만으로 핵심 source 부재를 corroboration으로 낮추지 않는다. 공식 공시·재무·현금흐름·revision 같은 primary family가 빠지면 CORE로 본다. 고객 공식·독립 보조 family는 각 affected component에 primary source-backed economic-role fact가 이미 있을 때만 corroboration이 될 수 있다. source-family binding이 불완전하거나 family가 알려지지 않았으면 CORE로 fail-closed한다.

쉬운 예: 회사 소개 fact 하나가 있어도 cash-flow statement가 없으면 CORE다. 반대로 issuer actual과 FCF가 있고 고객사 직접 확인만 없으면 해당 component cap으로 제한할 수 있다.

### 4. GitHub checkout 검사를 PR delta 기준으로 변경

base `main` 자체가 `output/**` 일부를 추적하므로 `test ! -d output`은 clean checkout에서 항상 실패했다. 이제 `origin/main...HEAD`에 새로 추가된 `.e2r_cache/**`, `data/cache/**`, `output/**`만 금지하고, 테스트 뒤에는 `git status --porcelain --untracked-files=all`로 새 찌꺼기를 검사한다.

### 5. CI가 실제 Gate 1 영수증을 검증하도록 변경

checkout 검사 다음 단계도 아직 존재하지 않는 Phase101 `canary_receipts/2026-07-12`를 요구하고 있었다. PR의 `offline-contract`는 현재 Git에 게시된 000660 compact receipt 4개 검사를 실행하도록 맞췄다. 이 검사는 raw 996 facts 재계산이 아니라 memo/Judge/score/Stage 영수증 일관성 검사다.

쉬운 예: 아직 만들지 않은 다음 학기 성적표를 요구하던 CI를, 이번 제출물에 실제로 들어 있는 Gate 1 검수표를 확인하도록 바로잡았다.

## 숫자가 왜 2,190 / 996 / 831로 다르나

- 2,190: historical lineage까지 포함한 전체 EvidenceFact 수
- 996: `CURRENT` 또는 `OPEN`인 동결 fact 수
- 831: StageCourt에 직접 인용 가능한 current/open fact를 eligibility와 citable lineage 규칙으로 투영한 수

예를 들어 superseded historical broker forecast는 전체 장부 2,190에는 남지만 현재 Stage를 정하는 831개에는 들어가지 않는다. 삭제한 것이 아니라 역할을 분리한 것이다.

## Stage 2가 된 이유

총점은 70.2이고 deterministic StageCourt는 Stage 2를 냈다. Green gate 네 primitive 중 두 개가 최종 present-positive 조건을 충족하지 못했다.

- `customer_preorder_or_allocation`: 고객 요청 물량 양산 mapping은 있으나 독립 source quorum 미충족
- `hbm_capacity_pre_sold`: CAPA 선판매·예약·완판 근거 없음

쉬운 예로 “고객이 요청한 HBM4 물량을 지금 양산한다”는 문장을 “향후 생산능력이 전량 장기 예약됐다”로 바꾸지 않았다.

## 남아 있는 한계

다음은 점수 상단과 confidence를 제한하지만 현재 score blocker는 아니다.

- HBM-only 매출·마진·FCF가 전사 actual과 완전히 분리되지 않음
- 고객별 signed 물량·가격·기간·취소·선수금·backlog/RPO 미확인
- HBM 전용 locked CAPA, sold-out 기간, realized ASP의 정량 근거 미확인

새 자료를 못 찾았다는 사실을 계약 부재로 바꾸지 않았고, 낮은 점수나 Stage 0으로 강제 종료하지도 않았다.

## legacy 원본과 clean PR 검증 범위

원본 `output/researcher_mode/c06/2026-07-12-clean-v8/`의 source corpus, 2,190 facts, 36 documents는 수정되지 않았다. copy-on-write root에서 계산했으며 source와 fact 파일 hash는 원본과 같다.

legacy copy-on-write 환경의 동일 입력 재실행 영수증에는 request, response, query, fetch, document, fact, score, Stage 파일 변화가 0으로 기록돼 있다. 세부 수치는 `identical_rerun_audit.json`에 있다.

하지만 clean PR에는 996개 fact 원장과 raw source checkpoint가 없다. 따라서 PR 단독 테스트는 70.2를 원천 fact부터 재계산하지 않고, 커밋된 compact 영수증의 내부 일관성을 검증한다. 이를 `clean-clone deterministic reproduction`이라고 부르지 않는다.

쉬운 예: 원본 장부 없이 합계표와 결재서의 숫자를 맞춰보는 것은 일관성 검증이다. 장부 996줄을 다시 scorer에 넣는 재계산과는 다르다.

## 아직 하지 않은 일

이번 목표는 Gate 1만 수행하도록 제한됐다. original goal의 Phase 101~109, 다른 archetype C08/C15/C17/C24/C28, KRX Census와 시장 전환 증명은 실행하지 않았다. Gate 1 결과를 외부 검토한 뒤 별도 단계로 진행해야 한다.

## 초기 실행 영수증과 후속 독립 검증

```text
focused regression: 221 PASS
full discovery: 7,204 PASS / failure 0 / error 0 / skip 0
Phase100 generated-artifact verification: 15 PASS
independent reviewer gate: READY / critical 0
Gate 1 Reviewer A~E: 5 PASS / critical 0
```

위 숫자는 초기 branch 내부 실행 영수증이다. 후속 독립 검수에서 generic gap 결박, gap별 acquisition coverage, source-role 정책과 CI checkout 검사를 고친다. 현재 PR head의 GitHub Actions가 green이 되고 외부 재검토가 끝나기 전에는 `CLEAN_PR_READY` 또는 merge 가능을 선언하지 않는다.

독립 검수 수정 뒤 raw가 없는 새 clean checkout에서는 full discovery 7,210개가 failure/error 0으로 끝났고 `OK (skipped=10)`을 확인했다. skip 10개는 모두 clean PR에 게시하지 않은 ignored/raw live leaf 의존성이 명시된 테스트다. Phase100 15개, Gate 1 tracked receipt 4개, production static audit critical 0, compileall도 통과했다. 정확한 GitHub 독립 머신 결과는 PR checks를 최종 기준으로 삼는다.

clean merge PR에는 과거 live/replay/cache 입력, raw 원문과 archive를 포함하지 않는다. 제외 artifact는 `external_artifact_receipt.json`에 상대 경로·크기·SHA-256만 기록했고 publication status는 `NOT_PUBLISHED`다. 대형 자료가 들어 있는 PR #5는 legacy review reference로 유지하며 새 clean PR만 병합 후보로 사용한다.
